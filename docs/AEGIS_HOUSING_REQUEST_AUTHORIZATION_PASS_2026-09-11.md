# AEGIS Housing Request / Authorization Pass — 2026-09-11

**Status:** IMPLEMENTED / NOT QUALIFIED
**Reference:** Canonical Lifecycle Contract v0.1
**Scope:** `AegisProm/AEGIS-housing-construction-v0.per`

## Result

Housing now implements the canonical request-identity and authorization boundary without collapsing placement, pending-foundation, or completion evidence.

Lifecycle:

```text
CIVILIAN DEMAND
  -> REQUEST ID
  -> AUTHORIZATION
  -> BASELINE CAPTURE / PLACEMENT-READY
  -> PHYSICAL BUILD REQUEST
  -> PENDING FOUNDATION
  -> COMPLETED-HOUSE OBSERVATION
  -> CAUSAL VERIFICATION GATE
  -> CONFIRMED only when causal evidence exists
```

## Identity

`aegis-hc-request-id` is derived from the originating civilian-demand generation and is not regenerated by the housing subsystem.

`aegis-hc-authorization-id` identifies the authorization associated with that request. Authorization generation must match the active housing request generation.

## Authorization

Authorization is distinct from `can-build` and from `(build house)`.

A physical build requires:

- valid housing request;
- current authorization;
- authorized stage;
- bounded attempt count;
- native `can-build house` feasibility.

The authorization is consumed when the build command is issued. A subsequent command therefore cannot reuse the same authorization.

Generation mismatch invalidates authorization and fails closed. Because no independently proven engine-time expiry mechanism is available in this slice, generation supersession is the explicit current-state expiry condition; this is not represented as a claim of native time-based authorization expiry.

## Placement and baseline

The pre-command completed-house count remains captured before the physical build request. This preserves the existing evidence boundary: later house-count growth is evaluated against the pre-command baseline.

No placement semantics were invented or replaced. The existing native `build house` endpoint remains the physical boundary.

## Pending foundation

`up-pending-objects c: house >= 1` remains an intermediate state.

It establishes pending/foundation evidence only. It does not establish completion.

The originating request identity remains attached to the lifecycle record while pending.

## Completion evidence

Completed-house observation remains independent from command issuance.

A completed-house count greater than the captured baseline sets `aegis-hc-world-evidence`.

That evidence is explicitly **not** treated as causal proof. Another house could have appeared through an independent or concurrent cause, so a count increase alone cannot receive request-level success credit.

## Causal verification

`aegis-hc-causal-evidence` is an explicit gate.

No current source rule is allowed to manufacture this evidence from the house count, pending state, or command issuance. Consequently, the confirmation transition requires both:

```text
WORLD_STATE_OBSERVED = 1
CAUSAL_EVIDENCE = 1
```

If the pending foundation disappears after world-state evidence has been observed but causal attribution remains unproven, the lifecycle enters explicit `CAUSALITY_UNPROVEN` failure rather than silently claiming success.

This intentionally leaves the slice **not qualified** until a separately proven causal-evidence mechanism is established.

## Idempotency

The existing one-attempt physical boundary remains. Authorization is also single-use because it is invalidated at command issuance.

A later retry must therefore come from a new demand/reassessment generation rather than repeated firing of the same request.

## Non-actions

This pass did not:

- treat `(build house)` as completion;
- treat a pending foundation as completion;
- infer causality from a count delta;
- introduce XS;
- copy runtime architecture into source;
- weaken the qualification registry;
- invent a native engine authorization clock;
- promote the slice to qualified.

## Qualification status

**NOT QUALIFIED.**

The physical lifecycle boundary is stronger, but promotion still requires engine/runtime evidence for request attribution, causal verification, explicit reassessment publication, and the remaining registry requirements.
