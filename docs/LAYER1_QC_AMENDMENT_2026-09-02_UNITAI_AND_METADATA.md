# Layer 1 QC Amendment — UnitAI and Metadata Pass

**Date:** 2026-09-02  
**Purpose:** Quality-control review of the preceding UnitAI/native metadata pass  
**Status:** Active research amendment; no framework implementation authority

## 1. QC verdict

The preceding pass contained substantial value, but its conclusions were slightly ahead of its strongest evidence in three places:

1. **Zero RIP-relative references is a representation constraint, not proof that the metadata is consumed indirectly.** The scan establishes absence of the tested direct addressing pattern. It does not identify the alternative mechanism.
2. **`currentOrder` versus `CurrentAction` is a strong architectural distinction, but native vocabulary alone cannot establish persistence, ownership, or exact temporal ordering.** Those must be promoted through state mutation evidence.
3. **The UnitAI feedback/recovery loop is a strong hypothesis, but diagnostic phrases do not by themselves prove that invalidation is synchronous, notification-driven, or followed by search in every case.** The causal path remains to be recovered.

These are corrections in precision, not reversals of the underlying research direction.

## 2. Important information that should be preserved

### 2.1 Negative reference evidence has high value

The complete `.text` Capstone scan returned zero direct RIP-relative references to eleven selected API signature/name addresses, the widened surrounding API-signature region, and selected UnitAI diagnostic strings.

The correct conclusion is:

> No direct RIP-relative consumer of the tested representation was recovered in the scanned `.text` interval.

The incorrect stronger conclusion would be:

> The executable does not reference these strings from native code.

The latter is not supported.

### 2.2 The failure changes search strategy

Because direct string references failed, the investigation should now search for **representation consumers**, not strings. Candidate mechanisms include pointers stored in tables, 32-bit relative offsets, compact indexes/ordinals, hash tables, initialization-time transformation, generated registration arrays, pointer-to-pointer structures, and dispatch records whose name/signature members are only one part of a larger record.

This is a methodological pivot and should remain prominent in future passes.

## 3. Deeper UnitAI interpretation

The most valuable conceptual result is not simply that UnitAI contains `currentOrder`, `CurrentAction`, targets, queues, and search diagnostics. It is that these concepts imply **different lifetimes and responsibilities may coexist inside one controller**.

A safer layered model is:

```text
REQUESTED WORK / ORDER
        │
        │ may persist while execution changes
        ▼
EXECUTION ACTION
        │
        │ requires current target/path/capability
        ▼
WORLD INTERACTION
        │
        ├── succeeds
        ├── fails
        ├── becomes invalid
        └── requires search/recovery
                │
                ▼
        STATE RECONCILIATION
                │
                ├── retain order
                ├── replace target
                ├── replace action
                ├── abandon/defer
                └── return idle
```

This is the most useful abstraction for subsequent native tracing because each arrow defines a potential state transition to locate.

## 4. New state-machine questions

### Order/action relationship

- Can an order survive an action failure?
- Can multiple actions realize one order?
- Can an action exist without an order?
- Can a new order replace an executing order immediately or only at a boundary?
- Does priority belong to the order, action, or scheduler around the controller?

### Target relationship

- Does target identity belong to the order, action, or controller-level state?
- Can target replacement occur without order replacement?
- Is target position cached independently of target identity?
- Does target type classify the target before or after selection?

### Notification relationship

- Are notifications generated by simulation objects, UnitAI subsystems, or both?
- Does notification processing mutate persistent state directly?
- Does notification processing enqueue work, invalidate action, or merely set flags?
- Is notification processing guaranteed before idle/order processing on the same update?

### Search relationship

- Does search return a candidate, mutate target state, or both?
- Is search invoked only after invalidation, or also proactively?
- Is search deterministic for identical candidate sets?
- Does search ranking depend on target value, distance, relationship, role, or hidden state?

These questions are much more likely to yield implementation evidence than additional string collection.

## 5. Stronger causal-spine target

The best next target is not necessarily the complete UnitAI `Update` function. A smaller verified mutation chain has greater evidentiary value:

```text
native function
    ↓
read one state field
    ↓
compare/branch
    ↓
write same or related field
    ↓
call/return
    ↓
next consumer
```

Preferred anchor fields, in descending value:

1. `CurrentAction`
2. `currentTargetID`
3. `currentTargetType`
4. `currentOrder`
5. `currentOrderPriority`
6. notification queue state
7. search-result/target state

Once one field's real mutation path is recovered, neighboring fields can be tested for shared ownership and lifecycle.

## 6. Identity investigation correction

The API signatures expose distinct query domains:

```text
unit → object identity
unit → copy identity
object + player → copy identity
unit → class
object + player → class
unit → type
object + player → type
object + player → valid/available
unit → garrison relationship
```

This establishes that the machine itself recognizes multiple identity/conversion operations. It does **not** establish that returned values are stable for the same lifetime, globally unique, or equal to replay references.

The next identity experiment should therefore be formulated as a conversion/lifetime test, not a numeric equality test.

## 7. Metadata dispatch experiment design

The next native scan should examine the bytes around the signature region for candidate references to the **region as a whole**, rather than exact string addresses.

Candidate patterns:

- absolute 64-bit pointers into `0x1432af000–0x1432b1fff`;
- 32-bit relative offsets into that region;
- arrays of monotonically spaced offsets;
- repeated records containing two pointers/offsets near each name/signature pair;
- code that iterates over the region using a count or sentinel;
- hash/index initialization that consumes the names.

A candidate becomes high-value only when code both reaches the region and performs an operation consistent with registration, lookup, indexing, or dispatch.

## 8. Predictive test refinement

The target-loss experiment should not initially attempt to prove the entire UnitAI loop. It should test one proposition at a time.

### Test A — action invalidation

Given a valid executing action, induce the minimum controlled condition that makes the target unusable. Measure current action, target identity, order, and notification state before and after.

### Test B — recovery/search

Repeat Test A while observing whether a search is entered and whether target state changes.

### Test C — order persistence

Determine whether the original order survives action invalidation.

### Test D — target replacement

Determine whether a new target can be selected while preserving the original order.

Together these tests distinguish competing architectures without assuming the answer in advance.

## 9. Programmer-intent QC

The preceding programmer-intent argument should be classified as **constraint-driven architectural inference**.

Strongly supported constraint:

> A game-world target can become invalid independently of the AI's original intention.

Plausible design response:

> Separate requested work from transient execution and provide recovery.

Not yet demonstrated:

> The original programmer intentionally implemented UnitAI around exactly that abstraction.

This distinction should remain explicit.

## 10. Layer 1 consequence

The pass materially strengthened the architecture model but did not justify a large numerical promotion by itself. The correct progress is qualitative:

- **Representation understanding:** improved.
- **UnitAI architecture hypothesis:** strengthened.
- **Predictive machine closure:** still incomplete.
- **Native implementation closure:** still the primary bottleneck.

The next promotion should come from a concrete consumer or state mutation chain, not additional vocabulary density.

## 11. Research rule added by this QC pass

> **When a representation-level scan fails, do not immediately infer an alternative representation. Enumerate competing representations and design a discriminating test for each.**

This prevents the investigation from replacing one unsupported assumption with another.

## 12. Repository integrity note

This amendment is a research record. It does not authorize framework implementation based on the hypotheses above. Proprietary executable material remains outside the public tree, and the publication gate remains independent of evidentiary confidence.
