# PUBLICATION AND RIGHTS CONTROL STANDARD — 2026-09-02

## Purpose

This document establishes the publication gate for material placed in the public `AiByz` repository. The repository is an engineering and research record, but public visibility does not itself establish a right to redistribute third-party material.

The governing principle is:

> **If ownership, license, authorization, or lawful publication basis is not established, the material does not enter the public repository merely because it is useful to the investigation.**

This standard applies to source code, scripts, documentation, reverse-engineering artifacts, executable-derived material, replay data, logs, screenshots, generated files, copied reference material, and third-party content.

## 1. Repository status

The repository is public. No repository `LICENSE` file was found on either the current engineering branch or `main` during this audit.

Accordingly, the project must **not** treat the absence of a license as permission to redistribute third-party material. GitHub's licensing guidance states that, absent a license, default copyright applies to the repository's own source and that rights to third-party content must independently be established.

This document is a publication-control policy. It is not a legal opinion and does not grant rights that the project does not possess.

## 2. Publication classes

### P0 — Safe project-owned material

May be published when it is authored by the project/user and contains no embedded third-party restricted material.

Examples:

- original ByzBot source code;
- original engineering documentation;
- original schemas and test harnesses;
- original analysis scripts;
- original measurements and derived tables;
- cryptographic hashes of locally obtained artifacts;
- methodology and experimental design;
- factual observations expressed in original wording;
- repository organization and provenance records.

### P1 — Third-party material with explicit publication rights

May be published only when the applicable license, permission, or other publication basis is recorded.

The repository must preserve attribution and license information where required.

### P2 — Third-party material with unclear rights

Do not publish the material itself.

A research record may instead contain a concise original description, provenance reference, identifier/hash, or link to the authoritative public source where doing so is appropriate.

### P3 — Proprietary executable/application material

Do not publish copies of proprietary executables, DLLs, game assets, private symbols, proprietary source code, or bulk extracted binary contents unless an explicit redistribution right has been established.

For native archaeology, prefer:

- executable name/version;
- SHA-256;
- local acquisition provenance;
- analysis methodology;
- original observations;
- small factual identifiers where appropriate;
- derived measurements;
- scripts that operate on a locally obtained copy.

The local proprietary artifact remains an input to the investigation, not a repository artifact.

### P4 — Decompiled/disassembled material

Do not publish substantial copied/decompiled/disassembled portions of third-party code merely because they were generated by an analysis tool.

Preferred publication form:

- address/range identifiers when useful;
- function or symbol identifiers;
- short necessary excerpts only when rights permit and publication is justified;
- original pseudocode summaries;
- structural descriptions;
- measurements;
- evidence classification;
- reproducible methodology.

A decompiler output is not automatically project-owned merely because the project generated the output.

### P5 — User/private/personal material

Do not publish personal information, credentials, tokens, private correspondence, private identifiers, or unrelated user data.

Replay data and logs must be reviewed for player names, chat, paths, account identifiers, machine identifiers, timestamps, and other information before public publication.

### P6 — Security-sensitive material

Do not publish credentials, authentication material, private keys, secrets, or material that would enable unauthorized access.

Security research must remain within applicable authorization and platform policy boundaries.

## 3. Required pre-publication checks

Before any new public artifact is committed, the engineer must answer:

1. **Origin:** Who created or supplied this material?
2. **Ownership:** Does the project/user own the material or have a publication right?
3. **License:** Is there an applicable license? If so, what does it permit?
4. **Authorization:** If not licensed, is there explicit authorization or another established legal basis for publication?
5. **Third-party content:** Does the artifact contain copied code, binary material, assets, documentation, logs, or data belonging to someone else?
6. **Personal data:** Does it contain personal/private information?
7. **Secrets:** Does it contain credentials, tokens, keys, or other sensitive security material?
8. **Derivation:** Is the artifact a transformation of third-party material rather than original project work?
9. **Necessity:** Can the engineering conclusion be preserved using an original description, measurement, hash, or reference instead of redistributing the underlying material?
10. **Provenance:** Can another engineer determine exactly where the evidence came from without requiring the repository to contain the restricted artifact?

If any material-rights question remains unresolved, publication stops at P2 rather than being promoted to public content.

## 4. Native archaeology publication rule

The Layer 1 investigation may publicly document what the project learned from a locally obtained executable, but the repository must distinguish:

`LOCAL INPUT -> ANALYSIS -> ORIGINAL OBSERVATION -> INTERPRETATION`

from:

`THIRD-PARTY ARTIFACT REDISTRIBUTION`

The first can often be represented through original documentation and reproducible methodology. The second requires an independent publication right.

Therefore, native archaeology dossiers should generally contain hashes, addresses/ranges, measurements, structural observations, evidence grades, hypotheses, and methodology rather than bulk binary dumps or substantial copied proprietary code.

## 5. Replay-data publication rule

Raw replay files are not automatically assumed safe for public redistribution merely because they were generated during the project.

Before publishing replay-derived artifacts, inspect for:

- player/account identifiers;
- chat content;
- machine paths;
- timestamps that create unnecessary personal exposure;
- embedded metadata;
- third-party fixtures or recordings not owned by the project.

Derived aggregate measurements and original analytical summaries are preferred over raw recordings when raw publication is unnecessary.

## 6. Existing repository audit consequence

The repository should be treated conservatively because it is public and currently has no repository-level license file.

Existing historical material must not be retroactively assumed authorized merely because it is already present in Git history. If an artifact is later determined to have unclear publication rights, it should be quarantined, replaced by an original research record where possible, or removed after provenance/legal review. Git history must be treated as persistent publication history rather than as an invisibility mechanism.

## 7. Evidence integrity and rights integrity are separate gates

An artifact can be scientifically valid but unsuitable for publication.

Conversely, an artifact can be publishable but scientifically weak.

Every public artifact therefore has two independent gates:

### Evidence gate

`Is the claim supported by the evidence?`

### Rights gate

`Are we authorized to publish the material used to communicate that claim?`

Both must pass.

## 8. Engineering default

When uncertain, publish less rather than more:

- original analysis instead of copied source;
- hashes instead of proprietary binaries;
- measurements instead of raw dumps;
- concise excerpts instead of bulk extraction;
- references instead of redistributed third-party documents;
- sanitized derived data instead of raw personal data;
- explicit hypotheses instead of overstated conclusions.

## 9. Project rule

No future GitHub commit should be justified solely by:

- "we found it";
- "it is already public somewhere";
- "the tool generated it";
- "the repository is public";
- "it helps the research";
- "other projects do it".

Those facts do not independently establish publication rights.

The project will maintain the stricter standard:

> **Evidence must justify the claim, and rights must justify the publication.**

## 10. Scope limitation

This standard is an engineering publication-control procedure, not legal advice. Copyright, contract, license, reverse-engineering, interoperability, privacy, and jurisdiction-specific questions may require professional legal review. Where a material publication decision turns on such a question, the conservative engineering action is to withhold the material until the applicable rights are established.
